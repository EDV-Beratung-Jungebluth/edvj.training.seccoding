 Phase 1 — Automatisierte Tests (Breite)

 1. Recon / Fingerprinting
   - Header & Tech-Stack: curl -sI http://localhost:3000 → X-Powered-By: Express, Cookie-Flags, fehlende
 Security-Header.
   - Exponierte Dateien prüfen: /package.json, /.git/, /.env, /node_modules/, Source-Maps (*.js.map), /robots.txt,
 /.well-known/.
   - Content-Discovery: ffuf -u http://localhost:3000/FUZZ -w <wordlist> (z.B. SecLists raft-medium-directories.txt).
 2. ZAP Spider + AJAX Spider + Active Scan (authentifiziert):
   - Traditional Spider + AJAX Spider (für JS-gerendertes Frontend) zum Crawlen aller Endpunkte.
   - Active Scan über den authentifizierten Context laufen lassen → findet Injection, XSS, Header-Probleme, etc.
   - Headless-Variante (Docker) für reproduzierbaren Report:
 docker run -t zaproxy/zap-stable zap-full-scan.py -t http://host.docker.internal:3000 -r zap-report.html
 3. nuclei: nuclei -u http://localhost:3000 -tags exposure,misconfig,cve,xss,sqli → bekannte
 Muster/Fehlkonfigurationen.
 4. nikto: nikto -h http://localhost:3000 → Server-Misconfig, veraltete Komponenten, gefährliche Dateien.

 Ergebnisse aller Scanner sammeln und als Ausgangsbasis für die manuelle Verifikation (Phase 2) nutzen — jeder
 Scanner-Fund wird manuell bestätigt (False Positives aussortieren).

 Phase 2 — Manuelle Tests pro OWASP-Kategorie (Tiefe)

 A01:2025 / A5:2017 — Broken Access Control (+ SSRF)

 - IDOR: ID-Parameter in URLs/Bodies hoch-/runterzählen oder fremde IDs einsetzen (/api/users/123 → 124), prüfen ob
 fremde Daten zurückkommen.
 - Forced Browsing: Admin-/geschützte Routen direkt aufrufen ohne Berechtigung (/admin, /api/admin/*) — mit normalem
 Account-Cookie.
 - Method/Verb-Tampering: GET vs POST/PUT/DELETE auf geschützten Endpunkten.
 - Fehlende serverseitige Prüfung: Aktionen, die im UI versteckt sind, direkt per API aufrufen.
 - SSRF (2025 hier eingeordnet): URL-Parameter, die der Server abruft (z.B. Webhooks, Image-Fetch, PDF-Render) auf
 http://localhost, http://169.254.169.254 (Metadata), interne Ports testen.
 - Hinweis: mit nur einem Account ist Cross-User-Testing eingeschränkt — Fokus auf vertikale Eskalation und IDOR mit
 eigenen vs. geratenen IDs.

 A02:2025 / A6:2017 — Security Misconfiguration

 - Security-Header prüfen: Content-Security-Policy, X-Frame-Options/frame-ancestors, Strict-Transport-Security,
 X-Content-Type-Options, Referrer-Policy, Permissions-Policy. (Express ohne helmet → meist alle fehlend.)
 - Cookie-Flags: HttpOnly, Secure, SameSite.
 - Verbose Errors / Stacktraces (Express Dev-Mode → komplette Stacktraces im Response).
 - Default-/Debug-Endpunkte, Directory-Listing, CORS-Fehlkonfiguration (Access-Control-Allow-Origin: * mit
 Credentials).
 - HTTP-Methoden: OPTIONS/TRACE erlaubt?

 A03:2025 — Software Supply Chain Failures / A9:2017 Verwundbare Komponenten

 - Black-Box-Fingerprinting: Express-Version aus Verhalten/Headern, Frontend-Lib-Versionen aus JS-Bundles, exponiertes
 /package.json oder package-lock.json.
 - Gefundene Versionen gegen CVE-Datenbanken / npm audit-Wissen prüfen.
 - Limit: ohne Quellcode/Dependencies nur oberflächlich — als Empfehlung aufnehmen, später npm audit / SBOM mit
 Code-Zugriff nachzuholen.

 A04:2025 / A3:2017 — Cryptographic Failures (Sensitive Data Exposure)

 - Transport: läuft alles über HTTP (kein TLS)? Werden Credentials/Tokens im Klartext übertragen?
 - Sensible Daten in Responses/Logs/JS (API-Keys, Tokens, PII, Session-IDs in URL).
 - Passwort-Speicherung indirekt prüfbar: bei „Passwort vergessen" altes Passwort einsehbar? Schwache Tokens?
 - Caching sensibler Seiten (Cache-Control).

 A05:2025 / A1+A4+A7:2017 — Injection (SQLi, NoSQLi, Command, XSS, XXE)

 - SQL/NoSQL-Injection: alle Eingabefelder & Parameter; sqlmap -u "<URL>" --cookie="<session>" --batch. NoSQL
 (MongoDB-typisch bei Node): {"$gt":""}-Payloads in JSON-Bodies / Login-Bypass.
 - XSS: reflektiert & stored — Payloads in Eingaben (<script>, "><img src=x onerror=...>), in Such-, Profil-,
 Kommentarfeldern; DOM-XSS in client-seitigem JS.
 - Command Injection: Felder, die an OS-Kommandos gehen (;id, | whoami, $(...)).
 - XXE: nur falls XML-Upload/-Endpunkte existieren — externe Entity referenzieren.
 - Template/Prototype Pollution (Node-typisch): __proto__-Payloads in JSON.

 A06:2025 — Insecure Design / A09:2025 — Logging & A10:2025 — Exceptional Conditions

 - Business-Logic: Workflow-Reihenfolge umgehen, negative Mengen/Preise, Race Conditions (parallele Requests), fehlende
 Limits.
 - A10 Exceptional Conditions / fail-open: ungültige/abnorme Eingaben senden (riesige Payloads, falsche Typen, fehlende
 Felder) → wird „fail-open" gewährt statt verweigert? Werden Fehler robust behandelt oder leaken sie Infos / hängen
 den Server?
 - A09 Logging/Alerting: existiert Rate-Limiting / Account-Lockout bei Brute-Force? Werden offensichtliche Angriffe
 blockiert? (Indirekter Black-Box-Indikator.)

 A07:2025 / A2:2017 — Authentication Failures

 - Brute-Force / Credential-Stuffing: kein Rate-Limit/Lockout? (mit Test-Account, vorsichtig).
 - Schwache Passwort-Policy bei Registrierung/Passwortänderung.
 - Session-Management: Session-Fixation, Token nach Logout noch gültig, fehlendes Session-Timeout, vorhersehbare
 Session-IDs.
 - JWT (falls genutzt): alg:none, schwaches Secret, fehlende Signaturprüfung, Token-Manipulation.
 - „Passwort vergessen"-Flow: User-Enumeration (unterschiedliche Antworten), schwache/ratbare Reset-Tokens.

 A08:2025 / A8:2017 — Software/Data Integrity & Insecure Deserialization

 - Unsichere Deserialisierung: manipulierte serialisierte Objekte / JSON mit unerwarteten Typen.
 - Fehlende Integritätsprüfung bei Updates/Uploads.
 - CSRF: state-ändernde Aktionen ohne CSRF-Token / nur Cookie-basiert (SameSite prüfen).
 - Datei-Upload: Typ-/Extension-Bypass, Pfad-Traversal beim Upload, Ausführung hochgeladener Dateien.
